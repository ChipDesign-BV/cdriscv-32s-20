# cdriscv-32s-20 on the ULX3S (ECP5)

> [!NOTE]
> **Status, 2026-09-06 — read this before quoting anything below.**
> This is a *bring-up procedure*, not a completed bring-up. What is
> **verified** in this repository is marked ✅; what is a documented
> recipe not yet run here is marked ⚠. Specifically:
> - ✅ the firmware image ([`fpga/ulx3s/firmware_smoke.hex`](../fpga/ulx3s/firmware_smoke.hex)) is real and **boots the core in simulation** through the actual QSPI loader path (the flasher `.bin` regenerates from it via `mkbootimg`).
> - ⚠ the ECP5 synthesis/place-route flow has **not been run** — `nextpnr-ecp5` is not installed in this container (only `nextpnr-ice40` is). The commands are the standard open ECP5 flow; they have not been executed against this design.
> - ⚠ an **FPGA-mappable TCM is a prerequisite that does not exist yet** (§3). The current SEC-DED TCM does not infer as block RAM.

## 1. Why this board

The design does not fit the Cyclone 10 LP on the Arduino Vidor 4000
(15,408 LEs / 504 kbit RAM): the two TCMs alone are ≈ 312 kbit and the
**dual-core lockstep** logic needs ~17–22k LEs (measured floor: 6,647
flip-flops from the ASIC synthesis, before combinational LUTs). Keeping
lockstep — the feature that makes this a *safety* subsystem — needs a
larger part.

The **ULX3S** carries a Lattice **ECP5 `LFE5U-45F`**: ~44k LUT4, ~1.9 Mbit
(108 × 18 kbit) block RAM, 28 DSP (18×18) blocks, and it has a **fully
open toolchain** (yosys + nextpnr-ecp5 + Project Trellis) — matching this
project's all-open ethos, no vendor licence. Board resources used here:

| ULX3S resource | Use |
|---|---|
| ECP5 LFE5U-45F | the subsystem (both lockstep cores + TCMs in BRAM) |
| 25 MHz oscillator | `clk_i` via an ECP5 PLL (the design closes 25 MHz) |
| on-board SPI flash (IS25LP128, shared with the bitstream) | the **firmware image**, read by the hardware QSPI loader |
| FT231X / `ujprog`/`openFPGALoader` | bitstream and flash programming |
| a button | `rst_ni` |
| LEDs | `err_pin_o`, `fault_any_o`, `core_sleep_o` for at-a-glance status |

Headroom check: 6.6k FF / 44k LUT is comfortable; ~312 kbit TCM against
1.9 Mbit BRAM leaves ample room. The design fits with margin — the work
is the TCM port (§3), not the capacity.

## 2. The firmware image ✅

The hardware QSPI loader (`rtl/boot/cdriscv_32s_20_qspi_boot.sv`) reads a
CRC32-checked image from SPI flash at power-up and streams it into the
TCMs before releasing the core — the same mechanism used on silicon, and
exactly what the ULX3S's on-board flash provides.

Build a bootable image from any program with the existing packer:

```sh
# assemble/compile a program to flat binaries first (build/prog.*.bin),
# e.g. via `make sw`, then:
python3 scripts/mkbootimg.py fpga/ulx3s/firmware_smoke.hex \
    --seg 0x00000000 build/prog.itcm.bin \
    --seg 0x10000000 build/prog.dtcm.bin \
    --bin fpga/ulx3s/firmware_smoke.bin
```

A pre-built example ships in [`fpga/ulx3s/`](../fpga/ulx3s/) as the
committed, text-form image [`firmware_smoke.hex`](../fpga/ulx3s/firmware_smoke.hex)
(the `.bin` the flasher wants is regenerated by the `mkbootimg` command
above — the repo ignores binaries as regenerable). The smoke program,
404 bytes, magic `0xCD20B007`, CRC32 `0x94bddc68`. It is not a sketch —
it is **verified to boot the RTL**:

```
$ vvp build/tb_cdriscv_boot.vvp +FLASH_HEX=fpga/ulx3s/firmware_smoke.hex
[TB] boot_done at cycle 6813
[TB] PASS after 7111 cycles (boot at 6813)
```

i.e. the loader validated the header and CRC, filled the TCMs, released
the core, and the program ran to its normal PASS. Program the `.bin` to
the flash at the loader's base offset (0, single-bit-read region — the
loader begins with the universal `03h` command):

```sh
openFPGALoader -b ulx3s -f -o 0x200000 fpga/ulx3s/firmware_smoke.bin   # ⚠ offset per your flash partitioning
```

Keep the firmware offset clear of the bitstream partition; the loader's
flash base is a parameter (`FlashBase`) on the boot module — set it to
wherever the firmware lives. Use `--quad` in `mkbootimg` (and matching
`FLAGS` bit 0) to have the loader switch to the `EBh` quad read for the
bulk once the header is in.

**Alternative load path (no QSPI flash):** for a quick logic-only bring-up
you can pre-initialise the TCM block RAM from a `$readmemh` file and set
`BootEnable=0`, skipping the loader entirely. A ready init file is
[`fpga/ulx3s/itcm_init.hex`](../fpga/ulx3s/itcm_init.hex) (one 32-bit word
per line, `scripts/mkimage.py`). This is the faster path to first-light;
the QSPI path is the one that mirrors silicon and exercises the loader.

## 3. Prerequisite: an FPGA-mappable TCM ⚠

The current TCM (`rtl/bus/cdriscv_32s_20_tcm.sv`) stores 39-bit SEC-DED
words with a read-modify-write on sub-word access. Measured 2026-09-06:
under yosys it **does not infer as block RAM** — it collapses to ~320k
flip-flops, which no FPGA will hold. Before a real ECP5 build, the TCM
needs a block-RAM-friendly variant:

- one true dual-nothing single-port synchronous array that maps to EBR
  (`$mem` inferrable: single clock, no async read, registered output);
- the (39,32) SEC-DED either kept (39-bit-wide EBR — ECP5 EBR is 18-bit,
  so 39 bits = 3 EBR wide, fine) or, for a functional demo, reduced to
  byte parity;
- selected behind the existing parameterisation, so the ASIC build keeps
  the macro-backed path and the FPGA build gets the inferrable one — the
  same split `BootEnable` already establishes.

This is bounded RTL work (a memory variant plus a bench), not a redesign,
and it is the one real gate between here and a bitstream.

## 4. The ECP5 flow ⚠ (procedure, not yet run here)

Once §3 lands, the open flow is:

```sh
# 1. synthesise for ECP5 (slang front end, as the ASIC flow uses)
yosys -m slang -p "
  read_slang --top cdriscv_32s_20_subsys_fpga <rtl file list>
  synth_ecp5 -json build/ulx3s/cdriscv.json"

# 2. place & route for the 45F, ULX3S constraints
nextpnr-ecp5 --45k --package CABGA381 \
  --json build/ulx3s/cdriscv.json \
  --lpf fpga/ulx3s/ulx3s.lpf \
  --textcfg build/ulx3s/cdriscv.config

# 3. pack the bitstream
ecppack build/ulx3s/cdriscv.config fpga/ulx3s/cdriscv.bit

# 4. load bitstream (volatile) then firmware to flash
openFPGALoader -b ulx3s fpga/ulx3s/cdriscv.bit
openFPGALoader -b ulx3s -f -o <FlashBase> fpga/ulx3s/firmware_smoke.bin
```

An FPGA top (`rtl/chip` is ASIC-pad-specific and not reusable here) must:
wrap `cdriscv_32s_20_subsys` with `BootEnable=1`; drive `clk_i` from an
ECP5 PLL off the 25 MHz oscillator; connect the QSPI pins to the on-board
flash (note the ECP5's dedicated `USRMCLK` primitive for the config-flash
clock — the flash SCLK cannot be a normal I/O on this device); and bring
`rst_ni`/`err_pin_o`/`fault_any_o`/`core_sleep_o` to a button and LEDs.
A `ulx3s.lpf` pin-constraint file is **not** committed here because it
must be validated against the specific ULX3S revision and cannot be
tested in this container; write it from the board's published pinout, and
mark it validated only after a real load.

## 5. What "bring-up" will and will not prove

On the ULX3S the design runs its real firmware from real flash through
the real loader, with lockstep active — a faithful functional bring-up.
It does **not** substitute for the ASIC signoff: FPGA fabric has its own
timing, no SEC-DED silicon behaviour, and none of the ASIC's physical
verification. It is a demonstration and a software-development platform,
not a safety-qualification vehicle. The safety evidence remains the
simulation, fault-injection and FMEDA work in
[verification_findings_20.md](verification_findings_20.md) and
[fmeda.md](fmeda.md).
